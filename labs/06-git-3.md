# Lab 6: Even more git
*October 22, 2026*

A third git lab seems kind of nuts, but even after all this I suspect many of you will run into new workflows and expectations that I haven't covered. It's a pretty complex system.

## Activity Description
In this lab, I will deliberately ask you to make some common mistakes so that you can learn how to fix them. These are:
- Cloning upstream instead of your fork
- Accidentally committing something and needing to go back and delete it
- Committing to the wrong branch

(Fun fact: I have made all of these mistakes. Sometimes repeatedly.)

Once more, we'll be working with the [`git-practice`](https://github.com/mru-open-source/git-practice) repo.

As you go through this lab, it might help to draw a diagram of your commits and branches to keep things straight. I may ask for a similar diagram on the midterm.

## Cloning upstream instead of your fork
1. Create a new fresh clone of https://github.com/mru-open-source/git-practice — *not* your fork.
   > To make things easier later on, consider adding a tag to this commit, e.g. `git tag lab_start`.
2. Working on the `main` branch, open your username file that you created in the first lab. It should be `userfiles/your-github-username.md`.
3. Make an edit of your choice. Tell a joke, perhaps, or maybe a link to an interesting article.
4. Commit your changes with a descriptive commit message, but **do not push**. You might actually be able to try to push, but hopefully I've set up the rules such that you don't have permissions to do so.

	(At this point, pretend that you've made more extensive changes and you really need to manage this with git rather than just recloning the correct repo.)

5. Tell git that the `origin` should actually be your fork by overwriting the url:
   ```bash
   git remote set-url origin <your-fork-url>
   ```
6. Do a `git fetch` followed by `git rebase` to fetch any changes that might be in your fork and apply your new changes to it. Resolve any merge conflicts before continuing to the next section.

## Remove something you committed by mistake
I added a top secret file to the repo that you cloned. It shouldn't be in your fork, so let's just pretend that you created it locally and realized your mistake before pushing. Fortunately, this is a scenario where you want to do a "dangerous" git operation, and it's easier to do it locally.

1. Still working on your `main` branch, find the commit hash one commit *before* the "top secret" file was added.
2. You have two options to skip over this commit, and probably more that I don't know about
   1. Interactive rebase (`rebase -i <hash>`) and just delete the top secret line
   2. Hard reset (`reset --hard <hash>`), then `cherry-pick` the subsequent commits (you'll be able to find their hashes in your `reflog`)

	It's up to you which one to do! Interactive rebase is probably easier, but it's a good excuse to practice a hard reset and cherry-pick to see what happens.
3. Check that your commit log doesn't have the offending commit anymore. Still **do not push** changes.

## Committing to the wrong branch
Oh no, all of this should have actually been done on a new branch! This is actually an easy fix, which is good, because it happens all the time.

1. Create a new branch with a name of your choosing from the existing commit.
2. Switch back to the `main` branch and do a hard reset to the state of the repo at the start of this lab. If you tagged your commit, you can use the tag name anywhere you would use a commit hash, e.g. `git reset --hard lab_start`. If you didn't, you can still get back to it by finding the commit in your `reflog`.
3. Switch back to your new branch and verify that the changes you made to your username file are still there.
4. Finally, push both branches (`main` and your new branch) to your forked copy of `git-practice`.

## Deliverables
Open a PR in the `git-practice` repository to merge in the changes from your new branch.
