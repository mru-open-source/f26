### Terminology
**Squash commits**: every time you make a commit to a branch with an open PR, the changes are reflected on that branch. Multiple commits are a great development habit, but can lead to a cluttered history. Many projects will ask you to "squash your commits" before a PR can be merged.

**Rebase onto main**: it can take time before your PR gets reviewed, and in the meantime, development in the target branch (usually `main` or `master` of the project's repository) continues. You'll need to fetch those changes from upstream and perform a `git rebase upstream/main` to stay up to date.

### Reviewer Role
> "Why are you repeating the same line of code? This looks like it could be a function."

A reviewer's job is to make sure the code meets the standards laid out by the project. This could involve commenting on your PR, or writing line-by-line comments in your code. For the PR that you are tasked to review:

1. Click on "Files Changed" to see what changed in the PR. Does it follow the instructions described in [last week's lab](02-git-1.md)?
2. If the submission isn't exactly as described in last week's instructions (e.g. updating the index in the wrong place), hover over a changed line and click the green "+" to add a comment where it needs to be fixed. You can either add a single comment with "Add a comment", or write multiple and submit them all at once with "Start a Review". A [graphical walk-through](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/commenting-on-a-pull-request) may be helpful.
3. If there is nothing that needs to be changed, add a comment of your choice just to practice it.
4. Go back to the "Conversation" tab. Add a comment saying whether changes are needed, and instruct your reviewee to squash their commits and rebase.
5. Wait for the reviewee to complete their task, then click what should now be a green "merge" button.

### Contributor role
> "This PR looks good. Squash your commits and rebase so I can merge it."

At minimum, most PRs need to be rebased onto the target branch before they can be merged. Squashing commits *can* be the job of the reviewer, but if you are asked to do it, it's good to know how!

> [!TIP]
> Git automatically pops open a text editor for a number of things. You can change the editor from the default `vi` to something more familiar, e.g.: `git config --global core.editor "code"` for VS Code.

1. Make sure you are working on your `dev` branch, or whatever you named the branch with your PR's changes.
2. Make any of the changes requested by your reviewer and commit them locally.
3. Fetch and apply changes from upstream:
    1. Configure a new remote named `upstream`:
        ```bash
        git remote add upstream https://github.com/mru-open-source/git-practice
        ```
    2. Fetch changes without merging them with `git fetch upstream`
    3. Rebase with `git rebase -i upstream/main`
4. The `-i` flag triggers an [interactive rebase](https://git-scm.com/book/en/v2/Git-Tools-Rewriting-History), which opens a text editor listing all your commits to your `dev` branch. Keep the first commit as `pick`, but change all subsequent commits to `squash` (or just the letter `s`). Save the file and exit the editor to continue.
5. You will have a merge conflict in `README.md`. Resolve by opening the file and editing it to reflect how you want it to look, which should be keeping all the additions. Git will add some `<<<===>>>` blocks to indicate where conflicts are occurring, e.g.:
    ```
    <<<<<<< HEAD
    This is a change from `main`
    =======
    This is a change to trigger a merge conflict
    >>>>>>> 114aa09 (Adding change from dev)
    ```
    Make sure to delete the git annotation lines, including the `=======` separator, then save the file. **Keep all the changes** so as not to delete other students' work.
6. Run a `git status`. It should say something about rebase in progress, instructing you to mark conflicts as resolved with `git add`. To continue the rebase, do the following:
   ```
   git add README.md
   git rebase --continue
   ```
   This will open a text editor with your commit message. Save and close the file to continue, or change the commit message if you like.
7. If there are multiple changes to `upstream/main`, you may need to keep repeating the last two steps until there are no more conflicts. At this point, your `dev` is up to date with `upstream/main`.
8. Finally, do one last `git push` and tell your reviewer to merge the branch. Since we've re-written history, you'll need to do a **force push** with:
   ```
   git push --force
   ```
