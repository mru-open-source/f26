# Continuous Integration and Deployment

**COMP 3700A: Contributing to Open Source** · November 2, 2026

## The Problem

Building a house takes many workers: plumbers, electricians, framers, and drywallers. Each one can do good work alone, but putting the work together often causes surprises. Software is the same. Code that works on your computer may break on someone else's. Small changes are also easier to combine than big ones.

## What Is Continuous Integration?

Continuous Integration (CI) is a cycle that repeats:

1. Make a change, such as a new feature or a bug fix.
2. Get the latest changes from the main project.
3. Fix any conflicts and build the code on your computer.
4. Push your changes.
5. A CI service automatically builds and tests the code.
   A common rule is that anything added to `main` must pass the CI tests.

## Problems CI Can Catch

Testing on your own computer can miss problems that CI finds:

- Your branch is out of date.
- The computer environment is different.
- You are using different versions of dependencies.
- Files are missing, or you forgot to commit something.
  Martin Fowler's writing on CI is the main reference for this topic.

## CI Services and YAML

Common CI services include GitHub/GitLab Actions, CircleCI, and Jenkins. Most of them use YAML files to set up their steps. YAML is easy for people to read. It uses indentation to show structure and `#` for comments.

The GitHub Actions example from class uses these parts:

| Key                        | What it does                                           |
| -------------------------- | ------------------------------------------------------ |
| `on: [push]`             | Runs the workflow every time code is pushed            |
| `runs-on: ubuntu-latest` | Chooses the computer that runs the job                 |
| `steps`                  | Lists the actions to run, in order                     |
| `uses:`                  | Runs a ready-made action, such as `actions/checkout` |
| `run:`                   | Runs a command, such as `bats -v`                    |

## CI/CD in FOSS Projects

FOSS projects have some problems that make CI harder than in most companies:

| Challenge          | Why it is a problem                                              |
| ------------------ | ---------------------------------------------------------------- |
| Cost               | Little money means less control over CI resources                |
| Security and trust | Some contributors may be harmful, so the system needs protection |
| Developer systems  | Contributors use many different computers                        |
| User systems       | The software must run on many different computers                |
| Experience         | Contributors have very different skills and levels of trust      |
| Code quality       | Messy code makes merging harder                                  |

## Takeaway

CI makes merging code a regular, automatic check instead of a surprise. This matters even more in FOSS, where there are many contributors and the maintainers may not know all of them.
